# 云记多语言（i18n）扩展方案设计

> 目标：语言文件统一放 `lang` 文件夹；首次启动自动释放「简体中文 / 繁体中文 / English」三份默认语言文件；
> 这三份同时作为模板供用户照着自建新语言；设置页可读取 lang 文件夹并列出的语言进行切换。
> 本文只讲架构与机制，不含实现代码。

---

## 一、总体架构（四层）

```
┌──────────────────────────────────────────────────────────┐
│ 第 4 层 前端层                                            │
│   LanguageProvider（Context） + t(key, params)            │
│   启动预读 → 字典加载 → 切换 → 回退                        │
│   设置页「语言」Tab：列表 / 切换 / 刷新 / 健康度提示         │
├──────────────────────────────────────────────────────────┤
│ 第 3 层 后端服务层（Rust 新模块 src-tauri/src/i18n/）      │
│   seed.rs    释放与升级                                   │
│   scan.rs    目录扫描、解析、校验、缓存                     │
│   dict.rs    回退合并（用户语言 ← 兜底字典）                │
│   3 个命令   list_languages / get_language / set_language  │
├──────────────────────────────────────────────────────────┤
│ 第 2 层 磁盘语言层（运行期，用户可见可编辑）                │
│   <exe 同级>/lang/*.json   ← 主位置                       │
│   <data>/lang/*.json       ← 只读场景下的兜底位置           │
├──────────────────────────────────────────────────────────┤
│ 第 1 层 内置种子层（编译期，唯一真源）                      │
│   仓库根 lang/zh-CN.json · zh-TW.json · en-US.json         │
│   Rust 用 include_str! 编进二进制；前端兜底也引用同一份      │
└──────────────────────────────────────────────────────────┘
```

**单一真源原则**：仓库根 `lang/` 是唯一维护点。Rust 编译期嵌入、前端兜底字典、运行时释放给用户，三者都从它派生，
避免出现「内置一份、磁盘一份、前端一份」的三处漂移。

## 二、文件组织方式

### 2.1 目录位置与优先级

| 位置               | 用途             | 说明                                                           |
| ------------------ | ---------------- | -------------------------------------------------------------- |
| `<仓库根>/lang/`   | 源码真源，进 git | 开发者维护，三份默认语言                                       |
| `<exe 同级>/lang/` | 运行期主目录     | 便携版场景下用户一眼能看到，双击即改                           |
| `<data>/lang/`     | 兜底目录         | 仅当 exe 同级不可写（装在 Program Files / 无管理员权限）时启用 |

启动时按「主目录 → 兜底目录」探测可写性（创建目录 + 写临时文件试探），选定后把该路径记入 `AppState.lang_dir`，
全程序统一走这一个路径，不做双目录合并（合并会让「我改了怎么没生效」无法排查）。

### 2.2 文件命名与内容结构

文件名即语言代码，采用 BCP 47 风格：`zh-CN.json`、`zh-TW.json`、`en-US.json`、`ja-JP.json`。
用户自建同样照此命名，例如复制一份改名 `ko-KR.json` 即被识别。

单文件结构（扁平 key + 内嵌元信息）：

```json
{
  "$meta": {
    "code": "zh-CN",
    "name": "简体中文",
    "nativeName": "简体中文",
    "version": 1,
    "fallback": null
  },
  "app.name": "云记",
  "nav.home": "首页",
  "settings.language.title": "界面语言"
}
```

设计取舍：

- **扁平 dot key，不用嵌套对象**。缺失项检测、回退合并、翻译者对照都是「key 对 key」，嵌套会逼着写递归合并；
  且扁平结构在 diff 里一眼能看出哪条变了。
- **`$meta` 用 `$` 前缀**，与业务 key 命名空间天然隔离，不需要额外排除逻辑。
- **`fallback` 字段**：允许某个语言包声明「我先回退到 X，再回退到 zh-CN」，例如 `zh-HK` 可声明回退 `zh-TW`，
  这样港式用语只需翻译与台湾不同的少数条目。默认三份都填 `null`。
- **单文件而非按模块拆分**：面向的是「用户手工复制一份去改」，一个文件打开即全貌最友好。
- **编码 UTF-8 无 BOM**，JSON 标准；读取时兼容带 BOM 的情况（先剥 BOM 再解析）。

### 2.3 随释放附带的说明文件

首次释放时一并写出 `lang/_README.txt`（下划线开头，扫描时跳过），内容说明：
文件命名规则、`$meta` 各字段含义、如何复制模板自建、缺失条目会回退显示中文、改完如何生效（设置页刷新 / 重启）。

### 2.4 key 命名规范

`模块.位置.语义`，全小写 + 点分。例：`nav.home`、`resource.card.delete`、`settings.tab.language`、`error.network`。
参数用 `{name}` 占位：`"resource.count": "共 {count} 篇"`。
复数按 `key.one` / `key.other` 两档（覆盖中英文足够，不做完整 CLDR 复数规则）。

## 三、初始化释放机制

### 3.1 时机

放在 `lib.rs` 的 `setup` 内，紧接 `create_dir_all(data_dir)` 之后、数据库与窗口创建之前。
理由：语言字典是纯本地资源，不依赖数据库；早于窗口创建可保证前端首帧就能拿到语言列表，不会出现「先中文后跳英文」的闪变。

### 3.2 流程

1. 解析 `lang_dir`（主位置可写性探测，不可写则落兜底位置），`create_dir_all`；
2. 逐个处理三份种子：
   - 目标文件**不存在** → 写入种子原文；
   - 目标文件**已存在** → **直接跳过，绝不覆盖**（用户可能已经改过自己的模板）；
3. 读 settings 键 `lang_seed_version`，与编译期内置的版本号比较：
   - 相等或更高 → 结束；
   - 内置版本更高 → 说明官方模板更新了，此时**不覆盖**已有文件，而是写出 `zh-CN.template.json` 供用户对照，
     并在设置页给出一行提示「官方语言模板有更新，可对照 xxx.template.json 补充」；
4. 写 `lang_seed_version = 当前内置版本`；
5. 执行一次目录扫描，结果缓存进 `AppState`；
6. **全程失败不阻塞启动**：任何一步出错只记日志并降级为「仅内置兜底字典」，保证用户永远能进程序。

### 3.3 幂等与升级

- 幂等靠「文件存在即跳过 + 版本号」，重复启动无副作用；
- 用户删掉某份语言文件后重启，会被重新释放（这是期望行为，相当于恢复出厂模板）；
- 程序自身升级替换 exe 时，`lang/` 不在安装覆盖范围内，用户改过的文件不受影响。

## 四、动态加载与切换逻辑

### 4.1 后端命令（3 个）

| 命令              | 权限                 | 作用                                 |
| ----------------- | -------------------- | ------------------------------------ |
| `list_languages`  | 所有用户（含未登录） | 扫描 lang 目录，返回语言清单         |
| `get_language`    | 所有用户             | 取指定语言的完整字典（已与兜底合并） |
| `set_ui_language` | 管理员               | 写入全局默认语言                     |

`list_languages` 返回项：

- `code` / `name` / `nativeName`（下拉里用 `nativeName` 显示更直观）
- `isSeed`：是否官方内置三份之一
- `coverage`：相对 zh-CN 的键覆盖率、缺失数 —— 用于设置页提示「该语言包缺 12 条，缺失部分将显示简体中文」
- `status`：`ok` / `invalid`，`invalid` 时带解析错误信息（「第 38 行 JSON 语法错误」），该文件不进切换列表

扫描结果在 `AppState` 内缓存；提供「刷新」入口重扫（用户运行中往文件夹丢了新语言包，点一下即可，不必重启）。

### 4.2 持久化：双层

| 层       | 存放位置                                                      | 含义                              |
| -------- | ------------------------------------------------------------- | --------------------------------- |
| 全局默认 | `settings` 表 `ui_language`，加入 `PUBLIC_KEYS`，默认 `zh-CN` | 管理员在设置页设定，全站默认      |
| 本地覆盖 | localStorage（沿用现有 `uiStore` 的持久化写法）               | 当前这台机器/这个用户自己选的语言 |

取值优先级：**本地覆盖 > 全局默认 > zh-CN**。
这样既满足「设置里切语言」，又让普通用户（非管理员）也能自己选界面语言，而管理员设定的默认值对所有人有效。

### 4.3 前端加载时序（避免闪变）

```
localStorage 读上次语言码 ──▶ 用内置兜底字典(zH-CN)先渲染首屏
        │
        └─▶ 并行：list_languages + get_language(code)
                │
                └─▶ 字典就位后替换 Context，触发重渲染
```

首屏直接用编译进前端的兜底 zh-CN 渲染，因此**永远不会有空白或英文闪一下**；
若上次选的是英文，则首帧是中文、字典到位后切英文（<100ms）。若要彻底消除，可把上次用过的整份字典也缓存进 localStorage，
启动时先用缓存字典渲染（字典体积仅几十 KB，可接受），再异步校验更新。

### 4.4 切换流程

1. 用户在设置页选择语言 → 调 `set_ui_language`（管理员）或仅写本地（普通用户）；
2. 调 `get_language(code)` 取回合并后的字典，写入 Context；
3. 同步 `document.documentElement.lang = code`（影响浏览器/系统的拼写检查、字体回退）；
4. Context 变更触发全树重渲染，**无需刷新窗口、无需失效 React Query 缓存**（业务数据与语言无关）；
5. 表单校验提示、Toast、Dialog 等动态文案随 `t()` 重算。

### 4.5 回退链（关键健壮性设计）

```
t(key):
  当前语言字典命中   → 返回
  fallback 链（$meta.fallback 声明的父语言）→ 返回
  内置兜底 zh-CN     → 返回
  都没有             → 返回 key 本身（开发期一眼看出漏翻）
```

这条链保证：**任何残缺的、用户瞎翻译的语言包都不会让界面出现空白或崩溃**，最差也是显示中文。
同时它也是「模板更新不必强制覆盖」的底气所在。

### 4.6 校验与错误呈现

- JSON 解析失败 → 该文件标 `invalid`，列表里灰显并附错误行号，不参与切换；
- 文件名 code 与 `$meta.code` 不一致 → **以文件名为准**，设置页给一条警告（避免用户复制后忘了改 meta）；
- 非法字符文件名（如 `新建文本文档.json`）→ 直接忽略，不进列表；
- 缺失键只统计不阻断；设置页可展开看「缺失键清单」，方便贡献者补翻译。

## 五、现有代码的迁移路径

界面文案目前硬编码在组件里，全量替换是大工程，建议分阶段：

- **P1 框架落地**：先做本文的四层骨架 + 三份语言文件（先只覆盖导航、设置页、通用按钮、错误提示等高频文案），
  跑通「释放 → 扫描 → 切换 → 回退」闭环；
- **P2 按模块抽取**：以路由为单位推进（列表 → 详情 → 编辑 → 管理后台），每完成一个模块补一次三份语言文件；
- **P3 兜底治理**：用脚本扫描 `src/` 里残留在 JSX 文本节点中的中文，输出待抽取清单，逐条清零。

配套两点：

- **类型安全**：以 `zh-CN.json` 生成 `TranslationKey` 联合类型（构建期脚本或 `keyof typeof zhCN`），
  `t('nav.hme')` 这类拼写错误在 `tsc` 阶段即报错；
- **开发期缺失登记**：`import.meta.env.DEV` 下 `t()` 未命中时，把 key 追加写入 `lang/_missing.json`，
  翻译时直接照单补，不用人工比对。

**Rust 侧文案**（托盘菜单「显示主窗口 / 退出」、窗口标题、部分错误提示）目前是中文硬编码：
P1 阶段先不动，P2 通过 Tauri 的菜单项 `set_text` 按当前语言动态改写；错误提示优先改为「错误码 + 前端 `t()` 翻译」，
避免后端为每种语言各存一份文案。

## 六、待确认的决策点

| #   | 问题                                       | 建议                                          |
| --- | ------------------------------------------ | --------------------------------------------- |
| 1   | 语言设置是全局（管理员统一）还是每人可自选 | 双层：管理员设全局默认，个人本地可覆盖        |
| 2   | 用户语言包缺条目时                         | 回退显示简体中文，界面不出现空白              |
| 3   | 官方模板更新后                             | 不覆盖用户文件，另出 `.template.json` 供对照  |
| 4   | 繁体中文                                   | 独立文件人工维护，不做简繁自动转换            |
| 5   | 日期/数字/货币格式                         | 走 `Intl`，随当前语言码自动切换，不进语言文件 |
| 6   | RTL（阿拉伯语/希伯来语）                   | 本期不做，仅预留 `dir` 字段                   |
| 7   | 运行时目录监听                             | 先用设置页「刷新」按钮，后续可加文件监听      |
